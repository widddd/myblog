# AUDIT-AGENTS-MECHANISM.md — 以 AGENTS.md 为核心的文档协作机制审计

> 类型：机制诊断（不是代码审计、不是需求清单）
> 日期：2026-02（本次会话）
> 范围：`AGENTS.md` + `docs/` 索引层 + 状态源 + 验证链路
> 方法：逐条读机制文件、对源码/package.json 交叉核对，反例全部带路径与行号
> 声明：本文件是**候选诊断**，不含已执行的机制改动；`docs/README.md` / AGENTS §3 尚未登记本文件（登记与否见 §4）

## 0. 机制快照（核对过的实测值）

| 载体 | 职责 | 实测 | 更新频率 | 谁在写 |
|---|---|---|---|---|
| `AGENTS.md` | 总纲：角色 + 红线 + 索引 + 工作流 + 状态 | **192 行**（自定上限 ≤400） | 每次交付（§6/§8 强制） | AI |
| `docs/README.md` | 阅读顺序 + 文档职责表 | 59 行 / 22 条职责行 | 新增 docs 时 | AI |
| `docs/agents-maintenance.md` | 触发同步表 + 健康度自检 | 44 行 | 每次交付 | AI |
| `docs/collaboration-workflow.md` | 任务隔离 + 授权 + Spec 流程 | 92 行 | 规则调整时 | AI + 用户 |
| `docs/ai/module.md` | 模块注册表（防重复造轮子） | 248 行 | 新增/改名源码文件 | AI |
| `docs/pitfalls.md` | 已知陷阱活文档 | **93 条 / 约 600 行** | 每次犯错 | AI |
| `changelog/*.md`（3 份） | 文件级改动 + 验证证据 | 只留本机 | 每批次 | AI |

**一句话结论**：这套机制的**内容质量很高**（红线具体、pitfalls 带实测数据、有 Spec 模板），但**运行方式不可靠**——全部依赖 AI 的自律与记忆，既没有执行器，也没有验证器，三层索引已经开始脱节。下面的问题按"机制层次"排列：执行器 → 同步 → 仲裁 → 归档。

## 1. 🔴 P0 — 机制没有执行器：所有约束都是"自觉条款"

### 1.1 没有一条规则是可机器校验的

全仓库搜索 `AGENTS.md` / `docs/ai/module.md` / `400 行` / `agents-maintenance` 出现在**任何** `.cjs/.mjs/.ts/.yml/.json/.sh` 中：**0 命中**；`.github/` 不存在（无 CI）。

于是这些"硬约束"全部只是文字：

| 约束 | 出处在哪 | 校验手段 |
|---|---|---|
| AGENTS.md ≤400 行 | AGENTS §0 | 无 |
| 交付前必须按触发表同步全部 docs | agents-maintenance.md:3-11 | 无 |
| 新增源码文件必须同步 module.md + AGENTS §3 | 触发表第 1 行 | 无 |
| 新配置字段必须"三处同步" | 触发表第 5 行 | 无 |
| 与 docs/ 冲突时以红线为准并修正 docs/ | AGENTS §0 | 无（只有在被人读到冲突时才可能触发） |

**后果**：规范的实际强度 = AI 当轮的注意力。任何一次长会话、上下文压缩或赶工，约束就静默失效——而失效**不报错**。

### 1.2 机制自带"反馈回路"，但从未运行过

`agents-maintenance.md:40-44` 的健康度自检问得很准：

1. 新会话的 AI 能否仅靠 AGENTS.md + docs/ 写出符合规范的代码？
2. pitfalls 增加后，重复犯错是否下降？
3. 是否还在同一对话纠缠超 10 轮？

**但三问没有责任人、没有周期、没有失败处置、没有历史记录。** 这正是本审计的价值：第 1 条被实际执行了一次，结果是首轮就发现索引脱节（见 §3.1）——说明这个回路是有用的，只是没人定期跑它。

### 1.3 知识只能"丢过才记"，没有前置推演

pitfalls 全部由真实事故产出（P-002 构建漂移、P-016 binding、P-084 越往右越糊……），而它们中有相当比例本可以在 Spec 阶段被推演出来——Spec 模板 `spec-template.md` §3 只问"是否破坏红线"，并不要求"列出本次新增的失败面"。

加上 `P-090` 的实测口径（"别靠眼睛，走 CDP 对比度审计"）这类**可执行验证法**被埋在陷阱条目里，机制的实际形态是：**踩坑 → 写长文 → 下次靠"记得读过"避免**。

## 2. 🔴 P0 — 同一规则多副本：同步成本是内容成本的数倍

同一信息在 2–6 处各存一份，任一处更新都要同时改其余几处：

| 信息 | 副本点 | 重复度 |
|---|---|---|
| **索引** | `AGENTS.md` §3（27 行目录表）+ `docs/README.md`（22 条职责表） | 各管一半，谁都不是全集（§3.1 已出事） |
| **pitfalls 摘要** | AGENTS §4（93 行全量清单）+ `docs/pitfalls.md`（93 条全文） | 摘要 = 全文的标题，**零信息增量** |
| **交付前检查清单** | AGENTS §8（12 项）+ `agents-maintenance.md:7-9` + `collaboration-workflow.md:53-57` | 三份清单内容重叠 |
| **任务隔离 / 10 轮阈值** | AGENTS §5 + `collaboration-workflow.md:7-18` | 同规则两处写 |
| **最小上下文包** | `docs/README.md:7-14` + `collaboration-workflow.md:20-28` | 同表两处写 |
| **人机分工表** | AGENTS §7 + `collaboration-workflow.md:83-92` | 同表两处写（后者多一行 COS SecretKey） |
| **触发表 vs 检查清单** | `agents-maintenance.md:15-28` + AGENTS §8 | 同一控制流的两个视图 |

**代价**：改一次协作规则要动 3–4 个文件；漏改一处就产生"两个版本的规章"，而 §3.2 说明这种冲突**没有仲裁人**。更关键的是：这些副本里有一条"自我矛盾"——AGENTS §4 的坑位摘要声称"全文见 docs/pitfalls.md"，那么它**只该有坑号+标题**，但它把"必须收 h1–h6""只输出 `--cell-*`""标题 16/14/14"等**完整行为约束**也写进了摘要，于是 93 行摘要成为实质事实源，与 pitfalls 全文构成双写。

## 3. 🔴 P0/P1 — 索引与状态：三种用法，全都在漏

### 3.1 索引层已经脱节（实测孤儿文件）

`docs/` 现有 29 个 `.md`。`docs/README.md` 职责表未登记的：**`m5-spec.md`、`geckoview-client-spec.md`、`android/README.md`**；`AGENTS.md` §3 目录导航中**没有任何 Android 相关行**（搜索 `android` / `geckoview` / `m5`：0 命中）。

而且 `geckoview-client-spec.md` 不是草稿——它含 GeckoView 版本锁定（`156.0.20260921121718`）、APK 体积实测（100–150MB/ABI，且要卡 nginx `client_max_body_size 512m`）、决策 D1–D4（含"是否进 GitHub 仓库"这类撞 P-092 的待决问题）。这棵树决定了一件**触及新顶层目录、新工具链、新依赖体系**的工作，却不在索引里、不在红线里、不在授权流程里——每一条都是新会话第一份必读文件**拿不到**的信息。

### 3.2 没有任何冲突仲裁机制

AGENTS §0 声明"全局硬性规则以本文件为准；与 docs/ 冲突时以红线为准并修正 docs/"——**这是写入时的优先级，不是发现时的仲裁流程**：谁去发现冲突？发现后谁修？修正范围多大？没有答案。所以当三处状态源互斥时（§3.3），机制无法自愈。

### 3.3 状态源三处互斥（实测）

| 位置 | 当前阶段表述 |
|---|---|
| `AGENTS.md:164` | 开头"**第三轮后台重写进行中**"，同一段结尾"**本轮…已提交为发行 0.1.1**（`changelog/` 三份清单即本版更新说明）" |
| `docs/ai/module.md:6` | "**项目当前阶段：M10 更新页数据清理已落地**；M9 程序更新与 M8 首页模块化已完成；M7 Linux 部署演练暂缓" |
| `AGENTS.md:164`（同段前文） | "…M10 数据清理、M9 程序更新与 M8 首页模块化已完成，本地发行 0.1.0" |

"进行中"与"已发行"同段并存，"当前阶段"两处不同。**§6 一行同时承担了：当前阶段、已完成清单、否决路线、vendor 基线、发行号**——且被规定为每次交付都要改（触发表最后一行）。状态与约束同寿，于是任何一次状态更新都要重写同一段，并行会话必然冲突（模块级红线，见 §4）。

### 3.4 "建索引"是明规则，"撤索引"没人负责

`docs/README.md:20` 只写"新增 docs 文件时更新"；`agents-maintenance.md:27` 只写"新增 docs 文件"。**没有任何地方写：更名、合并、废弃、归档时谁改索引。**

而 Spec 是有生命周期的（模板 §7 有"用户已批准/实施完成/文档已同步"复选框、`m3-spec.md` 自称"待审批"、`geckoview-client-spec.md` 自称"待审批"），但**任务收尾形态没有定义**：Spec 审批后去哪？实施后是否归档？docs/ 根会不会堆满"已实施的 Spec"？现在的答案：会——m2/m3/m4/m5/m6 都在根目录，且只有前三份被索引。

### 3.5 决策本身没有家

"为什么这么选"分散在：AGENTS §6（否决 Lucia / 自写 JWT / Drizzle…）、`module.md`（"后台配色的事实源""概览卡片的事实源"这类补充）、`HANDOFF.md`（冻结只读，不再维护）、`backup-restore-spec.md`（"历史 `oss` 当 `cos`"）、`geckoview-client-spec.md`（D1–D4）。

同一类信息五种格式、五处存放，且**唯一稳定的那一份（AGENTS §6）会被状态改写覆盖**。新会话想知道"当初为什么否掉 Drizzle"，得先猜它在哪个文件里。

### 3.6 目录不变量挡不住新维度

`AGENTS.md:9` 用"手册/总纲"分工，实际操作是"按目录分维度"：`docs/*-spec.md`、`docs/ai/`、`docs/android/`、仓库根 `*-PLAN.md`（`ADMIN-REWRITE-PLAN.md`）、仓库根 `changelog/`、仓库根 `HANDOFF.md`。**维度一增长（Android），索引就不够用了**——§3.1 的孤儿正是这个结构的产物，不是某人粗心。

## 4. 🔴 P0 — 交付物无版本：状态与规则同寿

| 现象 | 实测 |
|---|---|
| `changelog/` 三份清单是**文件级改动 + 验证证据**的唯一定所 | `changelog/*.md` 存在，且 `docs/README.md:38-40` 把它们写进职责表、AGENTS §6 把它们指定为"本版更新说明" |
| 但它们被规定**只留本机、不进仓库** | `docs/README.md:51,56`、AGENTS §2（P-092） |
| 连仓库根也没有版本可见性 | 无 CI、无 workflows；"当前发行"只在 `AGENTS.md:123,164` 与 `main/package.json:3`（`0.1.1`）三处人工重复 |

**后果**：
1. 证据只在那一台机器上——换机、重装、协作、事后复议，验证记录全部归零；
2. 远端 commit message 没有素材源（"直接摘取"的那份不跟随版本走）→ 要么照旧忽略，要么每次现编；
3. "这一版改了什么"至少有三处答案（AGENTS §6 的段落、changelog 三份、git 历史），互不引用、无主从关系。

## 5. 🟠 P1 — 文档不覆盖"怎么做才算过了"

### 5.1 "核心命令"清单漏掉了验证装备（实测）

`main/package.json` 的可运行命令：`dev`、`build`、`start`、**`lint`**、**`shot`**、**`test`**、**`db:seed`**、`setup`、**`restore`**、`pack:update`、`apply-update`。

`AGENTS.md:19` 的"核心命令"列了 8 项，漏了 `lint` / `shot` / **`test`** / `db:seed` / **`restore`**；`restore`、`shot` 只在 §3 路径表附带提及（单测则 0 次）。

而 `pnpm test` 实跑 **45 个测试文件**（`package.json:11` 逐项可数），却从未出现在任何"必读"清单里；"改代码前必读"缺"改代码后跑什么"。真实跑测试的依据散落在已实施的 Spec 里（`data-clear-spec.md:67`、`m3-spec.md:132`、`admin-ui-rewrite-spec.md:184`）——**通道依赖作者当时写了没写**。

### 5.2 验证知识被藏在"陷阱"里

- `pnpm shot`（2.6s 出图+量尺寸）是 AGENTS §4 里 P-086 的**一行摘要** + `collaboration-workflow.md:30-43` 的**一节**；
- `pnpm test` / `lint` / `build` 的必备性只在交付前清单（§8）暗示；`P-077` 的"工具输出也要交叉验证（pwsh 中文乱码、`Measure-Object -Line` 把 4444 行数成 3830）"埋在坑位第 77 条。

**没有"验证手册"，没有"什么时候跑哪条"的决策表**（改 UI → `shot`；改 lib → `test`；交付前 → `tsc` + `lint` + `build`；跨文件必跑回归）。结果：验证强度取决于当轮注意力，而不是机制。

### 5.3 环境事实同源缺失

"Windows 实测"（红线 §1、硬约束 1）、`NODE_OPTIONS=--max-old-space-size=768`（P-064）、"90 个文件以下的构建要多久"——分散在红线、坑位、Spec。新会话不知道**自己这台机器要满足什么、怎么快速确认**。机制里没有"环境自检"一节。

## 6. 🟠 P1 — 索引与事实源耦合：AGENTS 是路由表还是标准库

`AGENTS.md:12` 自称"单一事实源"，于是机制把**路由职责**（你该读哪份）与**标准职责**（你必须怎么做）压在一个文件里。实测代价：

- 每加一条硬规则，都要先过"会不会超过 400 行"这道闸（§0）；
- 于是新规则被判"不必立刻违反底线"→ 降级进 pitfalls；而 pitfalls 里真正带强制语义的又有一批（P-037 "禁止 CSS Grid 行跨越"、P-070 "不得重定义 `.heo-button`"、P-076 "禁止改 `--heo-*`"、P-091 的修法口径），再被 §4 摘要拉回 AGENTS；
- **通道是循环的**：AGENTS → pitfalls → AGENTS 摘要。任何"该放哪"的判断都在消耗同一份注意力预算，而不同会话给出的答案不一致（P-037 与 P-053 同族却分属两个层级）。

## 7. 🟡 P2 — 知识只增不减，没有生命周期

| 现象 | 实测 |
|---|---|
| 条目格式不统一 | P-001…P-010 是一条 `❌/✅` 短句（4–5 行）；P-078 起普遍带命令片段、实测数字、案例日期 |
| 编号序列被打破 | `P-084`（行 468）出现在 `P-083`（行 477）之前，随后是 P-085；编号 = 追加顺序，排序 ≠ 可检索 |
| 无分组、无标签、无"被引用"字段 | 无 `<!-- topic: css -->` 之类；`grep P-076` 之后无法知道它是否已被新规则取代 |
| 无失效机制 | 没有"已解决/已过期/被 X 取代"的状态位；P-005（vendor 漂移）与 P-029/P-030（不要改 vendor）说的是同一件事，而新会话必须同时记住两条 |
| 没有"下次该看哪条"的入口 | 93 条平铺，没有"改 CSS 先看 P-044/P-070/P-076/P-090/P-091"的索引 |

趋势：**每次事故 +1 条 +1 段长文**。到 200 条时，读它的成本会超过它避免事故的价值——而这一刻的止损信号（旧条目很久没被引用）目前**采不到**。

## 8. 🟡 P2 — 任务收尾没有被建模

机制只定义了"动手前"（最小上下文包 / 影响面分析 / Spec）与"交付前"（触发表 / 清单），**没有定义"任务关闭"**：

- Spec 审批后是否移动 / 归档？"已实施"由谁标记？
- 为什么 3 个 docs 文件会无人索引（§3.1）？——因为没有一步叫"本任务新增的文档登记进索引"。
- 为什么 `m5-spec.md` 会成为孤儿？——没有一步叫"Spec 生命周期结束时更新索引"。
- 会话产出（截图落 `main/.ui-shots/`，已 gitignore）与人看的手册（`user-manual.md`）之间没有交接。

## 9. 🟡 P2 — 规则执行成本 > 违反成本（摩擦层）

| 规则 | 摩擦 | 结果 |
|---|---|---|
| 同一会话不混做设计/实现/修 bug（§5） | 小 bug 也要开新会话 | 实际必然被绕过；绕过无后果 → 纪律整体贬值 |
| 纠缠 >10 轮就拆会话 | 无观测手段 | 靠自报；自报倾向"再做一轮" |
| "三处同步"配置字段 | 没有清单可勾 | 靠记忆；漏一处无人发现（P-004 就是这么来的） |
| 大改动先写 Spec | 接触点写"≥3 源码文件 / 改数据流 / 新增依赖 / 新增档案产物" | "一次 UI 调整"是否触发要靠猜；两类口径并存（AGENTS §2/§5 vs `collaboration-workflow.md:61`） |
| 每次交付都要动 AGENTS §6 | 状态与约束同文件 | 状态更新打扰所有人（缓存/注意力），且必然产生 §3.3 那种段落 |

**机制经济学的结论**：要让某条规则被遵守，得让"照做"比"绕过"便宜。现在多数规则相反。

## 10. 🔴 P0 — 策略冲突：想被 git 记住的东西，正是被清出仓库的东西

P-092 的成果（远端只留程序代码 + 项目文档）本身没问题，但"什么进仓库"的边界与文档机制冲突：

| 被排除的东西 | 它是什么 | 后果 |
|---|---|---|
| `changelog/` | 文件级改动 + 验证证据（AGENTS §6 指定的"本版更新说明"） | 证据不进版本控制 → 无痕、不可审计（§4） |
| `demo/` | 后台 UI 参照稿，**P-044 明确要求"改字号前先量参照稿"** | 权威参照物不在仓库 → 换机即失去对齐基准 |
| `reference/rules.md` | AGENTS §0 称其为"本项目规则体系由它搭建"的施工图纸 | 规则来源不可追溯，也不能被协作方查看 |

**这是一条比"文档写得好不好"更根本的策略问题**：把解释性材料（截图、参照稿、施工图、改动证据）清出仓库，就把版本历史变成了**唯一的解释来源**，而版本历史又没有人维护（§4）。

## 11. 问题优先级与重构方向

### 优先级（按"修一次能消掉多少条"排序）

**明确换来的是什么**：交付流程少一道手续、AGENTS 少一条耗时项、日常没有任何红绿压力。

**明确放弃的是什么**（不写下来就等于假装没有）：

1. 索引漂移只能靠人或 AI 的注意力发现——`m5-spec.md` / `docs/android/README.md` / `docs/geckoview-client-spec.md` 三个孤儿**当前仍然orphan**，AGENTS §3 里依旧没有 Android 那一维（新增顶层目录 + 新工具链的工作，新会话第一份必读文件里查不到）；
2. `AGENTS.md` §6 同一段里"进行中"与"已发行 0.1.1"并存，与 `docs/ai/module.md` 的"当前阶段：M10"互斥——**当前仍然互斥**，没有仲裁人；
3. `pnpm test` / `pnpm shot` / `pnpm lint` / `pnpm restore` / `pnpm db:seed` 仍不在 AGENTS §1 命令清单；改代码后跑什么，仍取决于当轮会话是否恰好知道；
4. `changelog/` 的证据不进仓库这条**没有变**（§4/§10），换机即失去验证记录。

**什么时候值得回头**：如果出现下面任一情况，把 §11 的 P0-1 重新拿出来议——(a) 同一条坑以同一形式第二次出现；(b) 索引漂移导致新会话做错事（不是"没读到"，是"读到错的/没得读"）；(c) 换机或换人接手，出现"文档与实际对不上且无人发现"。

**替代方案（不引入工具门槛的前提下，成本最低的两条）**：

- 把"当前阶段 + 已完成 + 否决路线 + 发行号"从 `AGENTS.md` §6 搬到 `PLAN.md` 或独立 `STATUS.md`，AGENTS 只留 1–2 行 + 链接 → 治 §3.3 的状态互斥，且不增加任何检查步骤；
- 给 `docs/geckoview-client-spec.md` / `docs/android/README.md` 补进 `docs/README.md` 职责表（两行字），消掉当前最危险的一个孤儿——它是唯一涉及**新顶层目录 + 新工具链**的文档。
